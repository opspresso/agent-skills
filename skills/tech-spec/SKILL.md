# TechSpec 작성

요구사항을 구현자가 의사결정과 검증에 바로 사용할 수 있는 기술 명세로 바꿔요.

## 입력 확인

먼저 다음 정보를 찾아요.

- 해결하려는 문제와 대상 사용자
- 현재 동작과 원하는 동작
- 성공 기준
- 기술·일정·호환성 제약
- 영향을 받는 시스템과 외부 의존성

입력이 충분하면 바로 초안을 작성해요. 중요한 설계 결정을 바꿀 정보가 빠졌을 때만
한 번에 1~3개의 구체적인 질문을 해요. 답을 몰라도 진행할 수 있는 내용은 합리적인
가정으로 표시하고 `Open Questions`에 남겨요.

## 설계 검토

다음 순서로 판단해요.

1. 문제와 해결책을 분리해요.
2. 요청한 범위와 명시적인 non-goals를 정해요.
3. 가장 단순한 구현안을 기본안으로 선택해요.
4. 실제로 고려할 가치가 있는 대안만 비교해요.
5. 데이터 흐름, 상태 변화, 실패 경로와 호환성을 확인해요.
6. 보안, 개인정보, 비용, 운영과 롤백 위험을 검토해요.
7. 각 단계에 검증 가능한 완료 조건을 붙여요.

근거 없는 기술 선택을 만들지 않아요. 저장소·API·조직 관례를 제공받지 못했다면
특정 구조가 이미 존재한다고 단정하지 않아요.

## 출력 형식

요청 맥락에 맞게 불필요한 섹션은 생략하되, 다음 구조를 기본으로 사용해요.

```markdown
# [기능명] TechSpec

## Summary
[문제, 제안, 기대 효과를 짧게 설명]

## Background
[현재 상태와 이 작업이 필요한 이유]

## Goals
- [측정 가능한 목표]

## Non-goals
- [이번 범위에서 다루지 않는 것]

## Proposed Design
[구성 요소, 책임, 데이터 흐름, 상태 변화]

## Alternatives
| 대안 | 장점 | 단점 | 결정 |
|---|---|---|---|

## Failure Handling
- [실패 조건과 처리]

## Security and Privacy
- [관련 위험과 대응, 해당 없으면 생략]

## Rollout and Rollback
- [배포 순서, 호환성, 관측, 롤백]

## Verification
- [테스트·측정 가능한 완료 조건]

## Milestones
1. [독립적으로 검증 가능한 단계]

## Open Questions
- [ ] [결정이 필요한 항목]
```

## 품질 기준

- 요구사항을 구현 세부사항으로 둔갑시키지 않아요.
- 목표와 검증 방법을 대응시켜요.
- 실패 처리에 “적절히 처리” 같은 모호한 표현을 쓰지 않아요.
- 대안은 기본안과 실질적으로 다른 선택지만 포함해요.
- 일정이나 수치를 근거 없이 만들어내지 않아요.
- 문서를 파일로 저장했다고 말하지 않고, 복사 가능한 Markdown으로 제공해요.
